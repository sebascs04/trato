# Ajustes de una adenda con TeTrato

El PDF adjunto y un contexto opcional del freelancer alimentan el mismo flujo `project_assistant` / `draft_change` del primer pedido. No se crea un segundo agente ni otro transporte de búsqueda.

1. La primera vista recibe un PDF y, opcionalmente, información adicional, por ejemplo una conversación en persona. Al continuar, el documento se registra mediante la ruta genérica de archivos con `kind=reference`, `purpose=addendum_adjustments` y la revisión enviada que recibió la respuesta. Todavía no se crea la siguiente versión de la adenda. El archivo ya tiene un vínculo al pedido aunque se cierre el formulario.
2. La ingesta común extrae texto, aplica el tratamiento correspondiente, prepara resumen y fragmentos e indexa mediante el file processor. La propuesta espera a que estén disponibles tanto el pedido original como el PDF de ajustes. Un fallo real se presenta con reintento explícito; no se redacta omitiendo esa evidencia.
3. El backend verifica propietario, proyecto, pedido, revisión actual enviada, ausencia de aceptación/pago/cierre y vínculo exacto del respaldo. Congela los términos de la versión enviada y las generaciones de documentos. El agente consulta pasajes mediante las herramientas existentes y debe citar acuerdo, pedido y ajustes. El contexto adicional se atribuye al freelancer, sin convertirlo en cita del PDF ni en aceptación del cliente.
4. Se reutiliza la vista de recomendación del primer pedido, incluido el modal de propuesta y sus fuentes. Después se muestran alcance y condiciones preparados, precio/fecha revisables y, al final, la comparación con la versión anterior y las opciones de guardado/envío. La tarifa y el precio siguen requiriendo revisión humana.
5. Confirmar crea la revisión con el comando de negocio existente. Un cambio del PDF o del contexto exige volver al primer paso y revisar una nueva propuesta. Se guarda el análisis original de esa versión solo si coinciden propuesta, versión anterior, documento de feedback y notas. Si no hubo contexto adicional, las notas de revisión se obtienen del razonamiento que el usuario acaba de revisar. Las citas se verifican literalmente contra las fuentes.

La versión enviada permanece inmutable; la nueva conserva su PDF, envío, aceptación y pago propios. Los documentos y revisiones siguen entrando en Documentos, Historial, grafo y consultas de TeTrato por los vínculos y comandos existentes. El recorrido anterior de respuestas recibidas por Gmail no se sustituye por una carga de archivo ni por datos simulados.

No hay migraciones, variables de entorno, tenants, proveedores ni dependencias nuevos. API y workers deben actualizarse juntos al publicar. La conexión real de Gemini, indexación y confirmación de v2 se prueba después por el usuario; las pruebas de contratos no se presentan como una ejecución E2E del modelo.
